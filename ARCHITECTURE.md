# Архитектура проекта User Management API

## Общая структура

Проект построен по слоистой архитектуре.

Основная идея разделения:

- **API** отвечает за взаимодействие с клиентом;
- **Services** содержит бизнес-логику приложения;
- **Repositories** отвечает за работу с данными;
- **Models** описывает структуру базы данных;
- **Core** содержит общие механизмы приложения;
- **DB** отвечает за подключение приложения к базе данных.


Слой взаимодействия с клиентом.

- обработка HTTP-запросов;
- проверка входных данных;
- вызов сервисов;
- формирование HTTP-ответов;
- работа с зависимостями FastAPI.

# Принципы архитектуры

В проекте используются следующие принципы:

- разделение ответственности между слоями;
- отсутствие бизнес-логики в HTTP-слое;
- отсутствие SQL-запросов в сервисах;
- централизованная конфигурация через переменные окружения;
- использование асинхронного доступа к базе данных;
- изоляция доступа к данным через Repository Pattern.

Такое разделение делает проект проще в поддержке, тестировании и дальнейшем развитии.

# Архитектурные решения

Во время разработки я старался разделить проект на отдельные части, 
чтобы каждая отвечала только за свою задачу. Это упрощает чтение кода и делает его проще в поддержке.

Бизнес-логика находится в сервисах, работа с базой данных — в репозиториях, 
а API занимается только обработкой запросов и ответов. 
Благодаря этому изменения в одном слое практически не затрагивают остальные.

Конфигурация приложения полностью вынесена в переменные окружения, 
поэтому проект легко запускать как локально, так и в Docker.

# Масштабирование

Сейчас проект рассчитан на небольшое количество пользователей и 
отлично подходит для учебных целей или небольшого сервиса.

При большом объёме данных можно заменить offset-пагинацию на cursor-пагинацию, 
добавить индексы для часто используемых запросов и вынести длительные операции в фоновые задачи. 
Это позволит приложению работать быстрее без серьёзных изменений архитектуры.
